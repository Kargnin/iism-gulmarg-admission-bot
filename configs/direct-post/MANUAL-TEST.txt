G1/G4 direct scripts: always-run retry mode

Continuous mode no longer reads or blocks on the original bot's pending, used-phone or booked records. It keeps retrying after timeouts, ambiguous replies, site rejections, Seat Not Available, Phone Already Registered and confirmed acceptance. This can resubmit an already accepted application. Stop it yourself with Ctrl+C when you want it stopped.

G1:
python3 /Users/bhushanmalani/Code/iism/configs/direct-post/post_g1.py

G4, in another Terminal tab:
python3 /Users/bhushanmalani/Code/iism/configs/direct-post/post_g4.py

No --confirm-not-booked flag is needed or supported. Existing history is preserved verbatim and is not used as a direct-request gate. The original bot's own behavior is unchanged. A second simultaneous copy of the same G1 or G4 worker is still blocked by the worker lock.

For one manual final-request attempt:
python3 /Users/bhushanmalani/Code/iism/configs/direct-post/post_g1.py --once
python3 /Users/bhushanmalani/Code/iism/configs/direct-post/post_g4.py --once

--once deliberately exits after one attempt. Default mode continues indefinitely, with no added HTTP retry sleep or backoff. Per-request network timeouts bound an individual connection; they do not stop continuous mode.

The terminal prints responseFile and responseMetadata. Manual results are stored separately in responses/once/G1 and responses/once/G4. Loop history retains the latest5 results per batch. A timeout has no new response body; its metadata explicitly records that. The latest attempt status is in G1-attempt-state.json or G4-attempt-state.json, and the latest confirmed success is retained in G1-last-success.json or G4-last-success.json. These are diagnostics, not stopping conditions.

Config is read before each iteration from /Users/bhushanmalani/Code/iism/configs/me.jsonc. Changes apply to the next request. Local-only edits rebuild the packet without server preparation; state, DOB, phone, course, level and batch changes refresh dependent server fields. Invalid/partial config or missing documents pause sending and resume after correction. In-flight values stay immutable until that request settles.

Fresh server preparation happens once at process startup and after explicit state rejection; preparation failures retry continuously. Server fee/allocation/age and signed fields remain server-owned. State, education, diet and all document paths come from config. documents.parentSignature explicitly selects the guardian upload. Normal-bot parallel/backoff settings do not control these independent direct workers.

The native state/history is neither cleared nor modified by the direct scripts. Status history can be inspected independently, but it never prevents sending. Keep your personal config and documents in their existing locations.
