Direct POST workers: G1 and G4

Configuration is read at the start of every request iteration from:
/Users/bhushanmalani/Code/iism/configs/me.jsonc

Edit the config while the updated worker runs. The next request uses a newly validated snapshot; an in-flight request keeps the old values until it settles. Invalid/partial JSON, invalid fields, or missing/invalid documents pause sending and automatically resume after correction. The worker never silently sends an old config while the current one is invalid.

Address/contact fields, education, diet and document paths come from config. Changed document contents at the same path are detected too. Local-only edits rebuild the multipart body without additional site preparation. State, DOB, phone and semantic course/level/batch changes invalidate dependent server preparation once. No fixed24-hour validity timer is used. ViewState/EventValidation errors trigger fresh server preparation.

Each live process prepares current server values once at startup, including availability. It then reuses matching state across final POST retries and adopts updated state from completed rejected forms. Fee and allocation are read from that prepared state, without a per-loop price/allocation query; for the existing profile these are10000, shared G1 allocation0 and G4 allocation7. Age is calculated only by the website. The existing confirmed G4 catalogue date typo is handled only for its original exact date range.

Guardian upload is now explicit in documents.parentSignature. It is currently signature.jpg, preserving your requested upload. A different configured guardian path is honored; clearing that required path pauses instead of silently substituting the applicant signature. Optional configured documents are included when applicable; removing one clears its upload flag.

Phone/target changes preserve used-number and booking history. An applicant name/father/DOB identity correction can rebind only an empty unsubmitted ledger. Existing submission/used-phone history blocks identity replacement. An unresolved final request retains its original phone/target and must be reconciled before a replacement can be sent. No progress reset or automatic history migration occurs. A season/run change requires a restart and does not touch the other run namespace.

Explicit bot.requestTimeoutSec and bot.submitTimeoutSec edits apply to subsequent requests. If omitted, direct mode retains its previous15-second preparation timeout and30-second final timeout. Direct workers still have no artificial HTTP retry delay; normal-bot parallel/backoff settings do not control these independent scripts. The brief local polling wait is used only while configuration is paused, not between valid HTTP retries.

Continuous use, in two Terminal tabs:

The commands above already prepare fresh state at startup. No separate --prepare-only command is needed before a live run. Restart existing old-version processes once to load this code; subsequent config edits need no restart.

Manual single-final-request tests, only after verifying an earlier pending attempt was not accepted:
python3 /Users/bhushanmalani/Code/iism/configs/direct-post/post_g1.py --once --confirm-not-booked
python3 /Users/bhushanmalani/Code/iism/configs/direct-post/post_g4.py --once --confirm-not-booked

--confirm-not-booked records your explicit confirmation and clears only that batch's pending marker. It cannot clear a confirmed booking or used-phone history. --once performs one final POST attempt after preparation; a complete no-seats reply exits1, meaning no application was confirmed. A possibly sent request without a verified reply stays pending.

Optional preparation for offline packet inspection (never submits):
python3 /Users/bhushanmalani/Code/iism/configs/direct-post/post_g1.py --prepare-only
python3 /Users/bhushanmalani/Code/iism/configs/direct-post/post_g1.py --plan

The terminal prints responseFile and responseMetadata. Manual responses are retained separately under responses/once/G1 and responses/once/G4. Continuous mode retains only the latest5 results per batch. HTML contains the response page; JSON includes status, headers, redirects and errors. A timeout has no new HTML body, so inspect responseReceived in the metadata. Seat Not Available is a retry condition for continuous mode. Ctrl+C stops a worker and preserves any unresolved final request.
